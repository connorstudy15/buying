# 知识检索查询优化 V2

## 为什么做第二版

第一版在多证据问题上出现了有效提升，但也暴露了三个问题：

1. 简单问题也会被改写，可能把原来正确的排序改坏。
2. 原问题和近似改写会分别加分，相当于同一个意思投了两票。
3. 融合后每篇文档只能保留一个片段，同一文档不同章节的必要证据会互相挤掉。

第二版只修这些已被评测证明的问题，不增加 BM25、重排模型，也不调整 RRF 的 `k=60`。

## 在线链路

```text
静态知识无法回答的边界检查
  -> 查询处理器（只调用一次大模型）
  -> DIRECT / REWRITE / DECOMPOSE 三选一
  -> 沿用现有“向量召回 + 标题/地域定向补召回”
  -> 按信息需求分组进行 RRF 融合
  -> 只合并同文档、同章节、高度重叠的片段
  -> 拆分模式优先保住每个子问题的一条合格候选
  -> Top-K
```

三种模式的含义：

- `DIRECT`（直接检索）：问题已经清楚，只查原问题，最终排序与旧链路完全一致。
- `REWRITE`（查询改写）：只有一个知识点，但说法不利于检索；同时查原问题和改写问题。
- `DECOMPOSE`（查询拆分）：问题包含至少两个独立知识点；查原问题和每个子问题，不再额外查全局改写。

## 防止重复投票

每条查询都有 `intent_group_id`（信息需求分组编号）。原问题和单需求改写属于同一个分组，
同一候选在组内只取最大一次 RRF 分数；不同子问题的分数才允许相加。

若改写与原问题的字符二元组 Dice 相似度达到 `0.92`，改写会被当作近似重复并改走
`DIRECT`。这个判断不调用 embedding，也不在冻结的 22 条发布评测集上反复调阈值。

## 去重和多证据保护

- 完全相同的片段仍然只保留一次。
- 只有“同一文档 + 同一章节 + 文本相似度至少 0.92”的片段才合并。
- 同一文档的不同章节允许同时返回；默认每篇文档最多保留两个片段。
- 上述每文档上限是软限制：候选不足时会放开，避免返回数量不足。
- `DECOMPOSE` 模式会为每个子问题优先选择一条分数达到最低可回答阈值的候选，再按总分补满。

这里的“某候选由某子查询召回”只是线上来源记录，不等于它一定是真正证据。真正的正确率仍由
冻结评测集中的章节和原文引用判定。

## 失败回退和观测字段

查询处理器超时、网关失败、JSON 不合法或关键约束丢失时，原样退回旧检索链路。
追踪和评测记录以下字段：

- `query_plan_mode`：本题选择了哪种模式。
- `intent_group_id`：查询属于哪个信息需求。
- `rewrite_similarity` / `rewrite_decision`：改写相似度以及是否被采用。
- `near_duplicate_decisions`：哪些片段因同章节高度重叠被合并。
- `provenance`：每个最终片段来自哪些查询、召回路线和名次。
- 融合前/后的信息需求覆盖率：用于判断证据是在初始召回阶段没找到，还是在融合阶段丢失。

功能仍默认关闭。必须完成同版本、同数据、同 Top-K 的旧链路与第二版成对评测后，才考虑上线。
