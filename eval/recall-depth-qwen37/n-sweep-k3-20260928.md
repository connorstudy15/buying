# Qwen3.7 候选深度 N 扫描（最终 K=3）

## 评测口径

- 数据集：`eval/product_recall.jsonl`，67 条 Query。
- 检索链路：Embedding → Qwen3.7 Text Rerank。
- 候选深度：N=4、8、12、16、24、32。
- 最终结果：统一截断为 K=3 后重新计算 Final Recall、Precision、MRR 和 nDCG。
- 所有档位实际策略均为 `embedding_rerank`，没有混入降级结果。
- 每档独立进程运行，避免本地嵌入式 Qdrant 的文件锁互相影响。

## 结论

- 质量优先时推荐 `N=24, K=3`。N=24 达到本轮最高 Final Recall@3、MRR@3 和
  nDCG@3，且 N=32 没有任何新增收益。
- `N=12` 是成本优先的备选：相比 N=8，Final Recall@3 提升 2.74 个百分点；
  N=16 虽提高候选覆盖，但没有让更多正确商品进入 Top-3。
- N=24 相比 N=12 再提升 1.49 个百分点，并把 Semantic Recall@3 从 0.9167
  提升至 1.0000，因此这一步仍有业务价值。
- 本轮 P95 不随 N 单调增长，说明网络和服务波动大于短商品文本增加带来的耗时；
  不能据单轮 733ms/790ms 判定 N=32 比 N=24 更快。应使用多次重复测量评估延迟。
- N=24/32 仍有三条候选未完全覆盖，均为预算、材质、配送等宽泛硬约束查询。
  继续扩大 N 已经无效，应通过结构化过滤前置或 Hybrid 召回处理。

## 剩余问题

- `300元以内抗造又不含塑料的旅行装备`：候选仅覆盖部分金标，并暴露一条
  “相关商品被硬约束过滤”的标注/业务规则冲突。
- `预算100元以内的收纳用品`：候选未覆盖金标。
- `500元以内能寄到欧洲的户外装备`：候选未覆盖金标。

这些问题不应靠把 N 从 24 增加到 32/64 解决。

## Reranker 成本补测

原 N 扫描评测器只记录延迟，没有保存百炼响应的 `usage.prompt_tokens`，因此上表
没有直接给出账单成本。随后使用同一 Query 和项目真实商品 `searchable_text()` 做
了一组 Token 实测：

| 候选深度 | 单次 prompt tokens | 单次费用 | 1,000 次查询 | 10,000 次查询 |
|---:|---:|---:|---:|---:|
| N=8  | 1,215 | ¥0.0006075 | ¥0.61 | ¥6.08 |
| N=24 | 3,363 | ¥0.0016815 | ¥1.68 | ¥16.82 |
| 增量 | +2,148 | +¥0.001074 | +¥1.07 | +¥10.74 |

费用按华北 2（北京）`qwen3.7-text-rerank` 官方原价 ¥0.5/百万输入 Token 计算，
未计免费额度与活动优惠。N=24 的 reranker 输入费用约为 N=8 的 2.77 倍；它不是
整条检索链成本的 2.77 倍，因为 Embedding 每个 Query 仍只调用一次、本地 Qdrant
不因 N 增加产生 API 费用、Agent LLM 成本也没有变化。

该表是使用真实商品文本的代表性单请求实测，不是 67 条原始评测运行的精确账单汇总。
要得到逐请求精确成本，后续应把百炼响应的 `usage.prompt_tokens` 写入评测 observation。
